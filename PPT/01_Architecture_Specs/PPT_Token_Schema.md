## Overview

This document defines the exact data structure of a minted Provisional Permission Token. It is the shared reference for every component in the PPT directory — the cryptographic pipeline produces it, the C-element gates on it, the formal verification models it, and the Lane 2 infrastructure cross-validates it at FPT issuance. Every other file in this directory assumes the schema defined here.

---

## Token Structure

A PPT is a signed, serialized data structure. All fields are included in the signed payload. No field is added after signing.

```
PPT {
    header: PPTHeader,
    payload: PPTPayload,
    audit: PPTAudit,
    signature: PPTSignature
}
```

---

## Field Definitions

### PPTHeader

```
PPTHeader {
    version:          uint8       // Schema version. Current: 0x01
    token_type:       uint8       // 0x01 = PPT; 0x02 = FPT (distinct token class)
    domain_id:        uint32      // Deployment domain identifier (operator-assigned)
    issuer_id:        bytes[16]   // HSM identifier — maps to FIPS 140-3 certificate
    issued_at:        uint64      // Unix timestamp, nanosecond precision
    expiry_bound:     uint32      // provisionalExpiry in milliseconds (operator-configured)
                                  // Default: 50ms for Lane 1 standard mode
}
```

**Notes:**
- `version` — schema versioning enables forward compatibility. Parsers must reject unknown versions.
- `token_type` — PPT and FPT share a common verification infrastructure; the type field prevents a captured FPT from being replayed as a PPT.
- `issuer_id` — binds the PPT to a specific HSM instance. Enables HSM compromise detection via anomaly analysis across issuer_id.
- `expiry_bound` — the hardware watchdog is configured to this value at PPT issuance. The watchdog fires at T = issued_at + expiry_bound.

---

### PPTPayload

```
PPTPayload {
    operation_id:     bytes[32]   // SHA-256 hash of the operation specification
    operation_type:   uint16      // Enumerated operation class (domain-defined)
    session_id:       bytes[16]   // Session context identifier
    principal_id:     bytes[32]   // Requesting principal — cryptographic identity
    nonce:            bytes[16]   // Hardware monotonic counter output — non-reusable
    execution_mode:   uint8       // 0x01 = provisional permitted
                                  // 0x02 = strict (FPT required before execution)
    dependency_id:    bytes[32]   // [optional] PPT token_id of a dependency
                                  // Set to zero bytes if no dependency
}
```

**Notes:**
- `operation_id` — the SHA-256 hash of the full operation specification prevents the PPT from being reused for a semantically different operation with the same identifier.
- `nonce` — generated by a hardware monotonic counter. Each nonce value is globally unique per issuer_id and never repeated. This is the primary replay prevention mechanism. Nonce exhaustion handling is an operator responsibility.
- `execution_mode` — determines whether provisional execution (State 1) is permitted or whether the system holds in State 0 until FPT arrival. Strict mode is mandatory for medical device actuation and autonomous vehicle commands.
- `dependency_id` — enables explicit dependency declaration between sequential PPTs. If set, the Lane 1 rendezvous point must confirm that the dependency PPT has reached State 2 before this PPT's FPT can transition the system to State 2. This is the specified mechanism for dependent PPT chain management.

### PPTAudit

```
PPTAudit {
    merkle_root:      bytes[32]   // SHA-256 Merkle root over the audit leaf set
    merkle_depth:     uint8       // Tree depth (log2 of leaf count)
    leaf_count:       uint32      // Number of leaves in the Merkle tree
    leaf_set_hash:    bytes[32]   // SHA-256 hash of the ordered leaf set
                                  // Enables leaf-completeness verification
    audit_seq:        uint64      // Monotonic audit sequence number
                                  // Enables gap detection in the audit log
}
```

**Notes:**
- `merkle_root` — anchors the PPT to the complete audit context at the time of minting. Cross-validated by Lane 2 infrastructure at FPT issuance — a mismatch between the PPT's merkle_root and the Lane 2 ledger's state at that audit_seq invalidates the FPT.
- `leaf_set_hash` — enables verification that the Merkle root was computed over the complete intended leaf set. Prevents an omission attack where a partial leaf set produces a valid Merkle root that excludes certain audit entries.
- `audit_seq` — enables detection of gaps in the audit log. A PPT with audit_seq = N+2 when the last confirmed audit_seq was N implies a missing audit entry, which should trigger an alert.

---

### PPTSignature

```
PPTSignature {
    algorithm:        uint8       // 0x01 = ECDSA P-256 + SHA-256
                                  // 0x02 = CRYSTALS-Dilithium (FIPS 204) [post-quantum]
    signature_bytes:  bytes[var]  // ECDSA P-256: 64 bytes
                                  // Dilithium: 2420 bytes
    public_key_id:    bytes[32]   // SHA-256 hash of HSM signing public key
                                  // Resolves to full public key via HSM key registry
}
```

**Notes:**
- `algorithm` — the algorithm field enables migration from ECDSA P-256 to post-quantum algorithms (CRYSTALS-Dilithium / FIPS 204, SPHINCS+ / FIPS 205) without schema change. Both algorithms must be supported by validators during the migration period.
- `signature_bytes` — the signature is computed over the canonical serialization of PPTHeader + PPTPayload + PPTAudit. The signature field itself is not included in the signed data.
- `public_key_id` — enables key rotation without embedding the full public key in every token. The HSM key registry maps key identifiers to current public keys and maintains historical keys for validation of tokens issued under prior keys.

## Canonical Serialization

The signed payload is the canonical serialization of PPTHeader + PPTPayload + PPTAudit using the following rules:

- Fields are serialized in the order defined in this document
- All integer fields are big-endian
- Variable-length fields are preceded by a 2-byte big-endian length prefix
- Zero-value optional fields (e.g., dependency_id when not set) are serialized as 32 zero bytes — they are not omitted
- No padding bytes between fields

The canonical serialization is the input to SHA-256 Stage 1 of the hardware pipeline. Any deviation from canonical form produces a different hash and an invalid signature.

## Token Size

| Algorithm | Header | Payload | Audit | Signature | Total |
|---|---|---|---|---|---|
| ECDSA P-256 | 29 bytes | ~115 bytes | 77 bytes | 64 bytes | ~285 bytes |
| Dilithium | 29 bytes | ~115 bytes | 77 bytes | 2,420 bytes | ~2,641 bytes |

The Dilithium token is approximately 9× larger than the ECDSA P-256 token. For deployments with constrained bandwidth or storage, this size increase has implications for Lane 2 anchoring throughput and should be accounted for in capacity planning during PQC migration.

## Token Lifecycle by Field

| Field | Set at | Used at | Immutable after signing |
|---|---|---|---|
| version | Minting | All validation points | Yes |
| token_type | Minting | All validation points | Yes |
| domain_id | Minting | Lane 2 routing | Yes |
| issuer_id | Minting | Anomaly detection | Yes |
| issued_at | Minting | `provisionalExpiry` calculation | Yes |
| expiry_bound | Minting | Hardware watchdog configuration | Yes |
| operation_id | Minting | Lane 2 cross-validation | Yes |
| nonce | Minting | Replay prevention | Yes |
| execution_mode | Minting | C-element mode select | Yes |
| dependency_id | Minting | FPT rendezvous check | Yes |
| merkle_root | Minting | Lane 2 audit cross-validation | Yes |
| audit_seq | Minting | Gap detection | Yes |
| signature | Minting (last) | All validation points | Yes |

All fields are immutable after signing. A PPT that has been modified in any field will fail signature verification.

## Validation Rules

A PPT is valid if and only if all of the following conditions are satisfied:

1. `version` is a known schema version
2. `token_type` is 0x01
3. `issuer_id` resolves to a known, active HSM in the key registry
4. `issued_at` is within the acceptable clock skew window (operator-configured; recommended ≤ 5 seconds)
5. `expiry_bound` has not been exceeded: current time < issued_at + expiry_bound
6. `nonce` has not been previously seen for this `issuer_id` (replay check against nonce log)
7. `leaf_set_hash` matches the hash of the provided leaf set
8. `merkle_root` is a valid root of the Merkle tree over the provided leaf set
9. `signature` is a valid signature over the canonical serialization of PPTHeader + PPTPayload + PPTAudit under the public key identified by `public_key_id`
10. `public_key_id` maps to an active signing key for `issuer_id`

Failure of any condition results in token rejection. The system remains in or returns to State 0.

## FPT Cross-Validation Fields

When the FPT arrives at the Lane 1 rendezvous point, the following PPT fields are cross-validated against the FPT:

| PPT field | FPT field | Validation |
|---|---|---|
| `operation_id` | `operation_id` | Must match exactly |
| `merkle_root` | `confirmed_merkle_root` | Must match exactly |
| `nonce` | `ppt_nonce` | Must match exactly |
| `audit_seq` | `ppt_audit_seq` | Must match exactly |
| `issued_at` + `expiry_bound` | (current time) | FPT must arrive before expiry |

A mismatch in any cross-validation field invalidates the FPT. The system remains in State 1 until a valid FPT arrives or `provisionalExpiry` fires.
